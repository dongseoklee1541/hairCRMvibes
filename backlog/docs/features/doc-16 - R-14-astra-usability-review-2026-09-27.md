# Astra 사용성 사전 검토 — 주 사용자 60대 여성

2026-09-27 후속: 아래 내용은 수정 전 검토 기록입니다. [수정·검증 결과](../history/doc-24%20-%20astra-feedback-remediation-2026-09-27.md)에 로컬 구현 완료와 미배포·실사용 미검증 범위를 정리했습니다.

## 범위와 판단 기준

사용자 요청으로 `main@76b64f60f594071583aea7c8a030c1a9ee095ff9`의 화면 코드·CSS·기존 R-14 문서를 GPT-6 Astra(ultra)가 읽기 전용 검토하고, 주 작업자가 주요 코드 근거를 대조했습니다. 주 사용자는 60대 여성이라는 가정이며, 스마트폰 숙련도·시력·보조 도구 사용·직원/관리자 역할은 아직 확인되지 않았습니다. 나이·성별로 능력을 단정하거나 시각 취향을 정하지 않습니다.

살롱의 고객 찾기 → 예약 등록 → 변경·금액 확인을 중심으로, 안내만 보고 다음 행동을 알 수 있는지, 잘못 눌렀을 때 복구할 수 있는지, 완료 여부가 분명한지를 검토했습니다. 아래 코드는 확인한 사실이고 사용자에게 미치는 영향은 실제 관찰로 검증할 가설입니다. 브라우저 렌더·실기기·실제 사용자 관찰은 수행하지 않았습니다.

## UX-1 · P1 · 새 예약의 고객이 의도 없이 선택됨

근거: `app/appointments/new/page.js:97-102`에서 전달받은 고객이나 기존 선택이 없으면 이름순 첫 고객을 자동 선택합니다. 일반 새 예약 진입에서도 고객 선택이 채워지므로, 날짜·시간·시술에 집중한 사용자가 잘못된 고객으로 등록할 위험이 있습니다. 연령과 무관한 데이터 오입력 위험이며 주 사용자의 완료 과제로 먼저 확인할 항목입니다.

권장: 고객 상세에서 전달한 명시적 고객은 유지하되, 일반 진입은 “고객을 선택해 주세요” 상태로 시작하고 선택 후에만 등록을 허용합니다. 개인정보를 추가로 보여주지 않고도 가능한 개선입니다. 동명이인 구분은 별도 설계 검토로 두며, 현재 이름-only 선택 계약을 깨면서 실제 연락처를 추가하지 않습니다.

확인 과제: 고객 상세가 아닌 예약 메뉴에서 “합성 고객 B의 내일 오후 예약을 등록해 주세요.” 누가 선택돼 있는지 사용자가 인지하고 설명하는지 관찰합니다. 현재 코드의 자동선택은 확인됐고 실제 오등록 빈도는 미측정입니다.

## UX-2 · P2 · 한 폼의 두 저장 버튼과 완료 판단

근거: `app/appointments/page.js:716-719`는 금액이 바뀐 상태에서 일반 저장을 누르면 별도 금액 저장부터 요구합니다. `1236-1267`에 “실제 금액 저장”과 “저장”이 함께 있으며, `1246`은 충돌 시 다른 수정 내용을 덮어쓰지 않는다는 구현 설명을 제공합니다.

권장: 데이터 동시성·별도 저장 계약은 유지하면서 “시술금액 저장”과 “예약 정보 저장”으로 범위를 구분하고 각 그룹의 미저장/저장완료를 표시합니다. 내부 충돌 설명 대신 “금액과 예약 정보는 각각 저장해 주세요”처럼 행동을 설명할 수 있습니다. 한 버튼으로 합치는 변경은 별도 데이터 계약 검토 없이 하지 않습니다.

확인 과제: 시간과 실제 금액을 함께 바꾼 뒤, 사용자가 두 변경의 저장 여부를 화면에서 설명하도록 합니다. 저장 횟수를 기억해야 하는지, 금액만 저장하고 모두 완료했다고 판단하는지 관찰합니다.

## UX-3 · P2 · 오류 안내가 실제 가능한 행동과 불일치

근거: `app/appointments/new/page.js:241-244`는 횟수권 조회 실패 시 “횟수권 없이 저장하거나 다시 시도”를 안내하지만, `359-361`과 `637-648`은 그 오류가 남아 있으면 제출을 차단합니다. 안내한 대안을 실행할 수 없습니다. 시술·휴무 조회 실패 영역(`473-476,503-509`)도 고객/횟수권 영역처럼 명시적인 해당 조회 재시도 경로가 제공되지 않습니다.

권장: 데이터 보호를 위한 저장 차단은 유지하고 오류 문구를 실제 동작과 맞춥니다. 실패한 영역 바로 옆의 “다시 불러오기”와 성공 후 등록 가능 상태를 연결합니다. staff에게 접근할 수 없는 설정 화면에서 시술을 추가하라고 안내하는 경우는 “관리자에게 시술 등록을 요청해 주세요”처럼 역할에 맞춰 구분합니다.

확인 과제: 합성 조회 실패를 주입하고, 새로고침이나 진행자 도움 없이 무엇을 해야 하는지 알 수 있는지 확인합니다. 문구/제출 조건 불일치는 코드로 확인했으며 사용자 반응은 미관찰입니다.

## UX-4 · P2 검증 후보 · 좁은 화면 달력의 가로 터치 영역

근거: `components/appointments/AppointmentDatePicker.module.css:25-29,51-54,71-72`는 폭 100% 이하의 패널, 좌우 16px padding, 7열·6px gap, 날짜 셀 최소 높이 44px을 사용합니다. 가로 최소 44px은 별도로 보장하지 않습니다. 패널이 360px이고 다른 규칙의 영향이 없다는 가정에서는 `(360 - 32 - 36) / 7 ≈ 41.7px`입니다.

권장: 좁은 폭의 간격·padding을 조정할 수 있는지 검토하고, 열린 달력에서 날짜 버튼의 실제 가로·세로 hit area와 인접 날짜 오선택을 측정합니다. 전체 화면의 가로 스크롤을 만드는 최소 폭 강제는 피합니다. 기존 390×844·360×800 검증 기록을 현재 컴포넌트의 실측으로 간주하지 않습니다.

이 값은 CSS 기반 추정이며 렌더 측정이나 접근성 준수/위반 판정이 아닙니다. 이번 검토로 보류된 실기기 검증을 재개하지 않습니다.

## UX-5 · P2 · 로그인 실패 후 안내와 입력 확인 부족

근거: `app/login/LoginPageClient.js:40`은 오류 원문을 그대로 표시합니다. 이메일/비밀번호 label(`55,70`)은 input id/htmlFor로 연결되지 않았고, password 입력(`72-80`)에는 표시 전환이 없습니다. 오류 문구 영역(`84`)에도 명시적 alert/live 속성이 없습니다.

권장: 알려진 실패를 짧은 한국어와 다음 행동으로 매핑하고, 입력 label을 연결합니다. 비밀번호 표시 전환은 기본 숨김·명확한 라벨을 유지하는 선택지로 검토합니다. 비밀번호 재설정이나 새 계정 provisioning을 이 사용성 검토만으로 추가하지 않습니다.

확인 과제: 합성 잘못된 비밀번호·연결 실패에서 사용자가 입력을 확인하고 다음 행동을 설명할 수 있는지 검증합니다. 어떤 영어/기술 오류가 실제 표시되는지와 접근성 도구의 실제 동작은 미검증입니다. 모바일 로그인 실검증 보류는 유지합니다.

가독성 추가 확인 후보: `components/settings/RoleManagementPanel.module.css:289`의 역할·수락 상태 배지 11px, `app/login/page.module.css:30`의 로그인 오류 13px, `app/appointments/page.module.css:71`의 경고색 텍스트를 실제 화면에서 확인할 필요가 있습니다. 코드상 크기·색 토큰만 확인했으며 실제 읽기 실패나 대비 부족은 판정하지 않았습니다.

## 유지할 기반과 실제 관찰 계획

기본 본문·입력 16px, 보조 14px과 44px 조작 기준, 주요 메뉴의 한글+아이콘, 저장 중·오류 표시, 합성 데이터 사용 원칙은 이미 마련돼 있습니다. 단순히 글자를 일괄 확대하거나 기능을 추가하는 대신 위 막힘을 우선합니다. 실제 대비·글자 확대 시 잘림·키보드 가림은 이번 코드 검토만으로 통과 판정하지 않습니다.

[대표 사용자 프로토콜](doc-18%20-%20R-14-user-validation-protocol.md)의 고객 찾기·예약 등록·예약 확인/변경 과제와 도움 없는 완료·완료 확신 분리 기록을 재사용합니다. 기존 문서는 50~60대 여성 2명 조건의 준비 자료입니다. 이번 주 사용자 가정에 맞춘 후속 관찰은 60대 사용자를 중심으로 하되, 평소 쓰는 확대·안경·입력 방식과 업무 역할을 확인하고 사용자의 행동을 관찰합니다. 과제를 성공시키려고 정답이나 버튼 위치를 미리 알려주지 않습니다.

우선순위는 UX-1 오등록 위험 → UX-3 오류 복구 → UX-2 완료 확신입니다. UX-4는 화면 실측 후 판정하고, UX-5는 로그인 검증 재개 범위와 함께 다룹니다. UI 변경은 Pencil SSOT와 관련 회귀 검증 절차를 따릅니다. 이 피드백은 구현 승인이나 실제 참가자 결과가 아니며 R-14는 **구현 완료·대표 사용자 검증 대기**를 유지합니다.

[별도 R-10 보안·재시도 피드백](doc-11%20-%20R-10-astra-review-2026-09-27.md)의 F1/F2는 초대 활성화 전 해결할 항목입니다. 예약 사용성 문제와 섞어 실제 보안 결함의 우선순위를 낮추지 않습니다.
